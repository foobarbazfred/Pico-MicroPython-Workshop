## What this is

このリポジトリは、Raspberry Pi Pico 2 W と MicroPython を使い、GPIO、ADC、PWM、各種センサ、表示装置、ネットワーク、MQTT、IoT 連携までを扱う、2日間のハンズオン教材です。教材の題材は豊富で、受講者が1日目に基礎を学び、2日目にチームでプロトタイプを作る構成になっています。

### Stack

- **Language(s):** MicroPython / Python、Markdown、HTML/JavaScript
- **Framework / runtime:** Raspberry Pi Pico 2 W / RP2350、MicroPython
- **主な技術:** GPIO、ADC、PWM、I2C、SPI、UART、I2S、Wi-Fi、HTTP、MQTT、Node-RED
- **主なデバイス:** SCD41 CO₂センサ、LCD、サーボ、NeoPixel、SDカード、距離センサ、GPS、カメラなど

## How it's organized

```text
1-Workshop Guidelines/   研修方針、タイムテーブル
2-Training-Equipment/    使用するPico、キット、追加部品、参考資料
3-Day1-Foundation/       1日目の基礎教材、サンプルコード、画像
  ├─ GPIO / ADC / PWM
  ├─ センサ・I2C・SPI・UART
  ├─ LCD・SDカード・音声・カメラ
  ├─ Wi-Fi・HTTP・MQTT・Webサーバ
  └─ src/                 Picoに転送するサンプルコード
4-Day2-Practical/        チームによる実践課題、IoTダッシュボード
5-Future-Work/           今後の発展課題
```

**全体の流れは良いです。** 特に、`LED → GPIO → ADC → PWM → センサ → 表示 → ネットワーク → チーム開発` という方向性は、組み込み・IoT教材として自然です。

ただし、現状は「教材として完成している部分」と「アイデア・メモ段階の部分」が混在しています。受講者向けのテキストとしては、まず1日目の必須範囲を絞り、各章の到達目標と演習結果を明確にすると、かなり分かりやすくなります。

# 分かりやすい点・分かりにくい点

## 分かりやすい点

- 画像や回路図が多い
- 実行例を掲載している
- ピン番号を具体的に書いている
- REPLで確認する手順がある
- 実際の部品名、I2Cアドレス、通信方式が書かれている
- 受講者が最終的に作るアプリの例が豊富

## 分かりにくい点

### 1. Pico WとPico 2 Wの表記が混在しています

READMEでは「Raspberry Pi Pico W」と書かれている箇所と、「Raspberry Pi Pico 2 W」と書かれている箇所があります。

教材の最初に、次のような注意書きを置くとよいです。

> 本教材では Raspberry Pi Pico 2 W を使用します。  
> Pico W、Pico 2、Pico 2 Wでは、CPU、ピン機能、MicroPythonの対応状況が異なる場合があります。

また、「RP2」はMicroPythonのRP2ポートを指す場合もあり、Pico 2 Wそのものの略称としては少し紛らわしいです。教材内では、基本的に `Pico 2 W` または `Pico 2 W / RP2350` と書く方が安全です。

### 2. 基本用語の説明が急に専門的になります

例えばI2Cの説明では、プルアップ、マスター、スレーブ、ハードウェアI2C、ソフトウェアI2C、レジスタアクセスまで一度に登場します。

初心者には、まず次の3点だけで十分です。

1. SDAとSCLの2本で通信する
2. デバイスごとにアドレスがある
3. `i2c.scan()` で接続確認できる

その後に必要であれば、

- プルアップ抵抗
- ハードウェアI2C / SoftI2C
- レジスタ
- データシート
- 通信速度

を説明する方が理解しやすいです。

### 3. 回路図だけでは配線できない受講者もいます

各デバイスについて、回路図に加えて次の表があると非常に親切です。

| Pico 2 W | デバイス | 用途 |
|---|---|---|
| GP4 | SDA | I2Cデータ |
| GP5 | SCL | I2Cクロック |
| 3V3 | VCC | 電源 |
| GND | GND | グランド |

「物理ピン番号」と「GPIO番号」を必ず分けて記載してください。LEDのページでもこの注意点に触れていますが、各ページに毎回ピン表がある方が事故を防げます。

# 追加した方がよい課題

## 1. デバッグ課題

単に完成コードを実行するだけでなく、意図的に問題を発見する課題を入れると学習効果が高いです。

### 課題例

- LEDのGPIO番号を間違えるとどうなるか
- `Pin.PULL_UP` を外すとスイッチ入力はどうなるか
- I2Cデバイスを外した状態で `i2c.scan()` を実行する
- LCDのアドレスを `0x27` から `0x3f` に変更してみる
- センサの配線を1本外して、例外を確認する
- Wi-Fiのパスワードを間違えた場合の処理を追加する

## 2. スイッチのチャタリング対策

現在のスイッチ例は、押している間LEDを点灯するだけなので分かりやすいです。ただし、実用的な入力処理として次の発展課題を加えるとよいです。

- 押した回数を数える
- 押した瞬間だけ検出する
- チャタリングを除去する
- 長押しと短押しを区別する

## 3. `sleep()`を使わない制御

現在のサンプルは `time.sleep()` が多く、初心者には理解しやすい一方、複数の処理を同時に行う段階で限界が来ます。

次の課題を追加すると、2日目の実践開発にもつながります。

- LEDを点滅させながらセンサを読む
- センサを定期的に読みながらスイッチ入力を受ける
- `time.ticks_ms()` を使った非ブロッキング処理
- 状態機械による処理
- `asyncio` / `uasyncio` の紹介

## 4. センサ値の品質を扱う課題

センサは「値が読める」だけではなく、実際にはノイズ、遅延、校正、異常値があります。

追加課題として以下が適しています。

- 移動平均を実装する
- 最小値、最大値、平均値を記録する
- センサ値が異常な場合に警告する
- CO₂値が一定以上になったらLEDを点灯する
- 温度・湿度・CO₂をCSV形式で保存する
- センサ値に単位を付けてLCDへ表示する

## 5. 統合課題

1日目の最後に、15〜30分程度の小さな統合課題を置くと、2日目への橋渡しになります。

### 推奨課題

> SCD41でCO₂を測定し、CO₂濃度に応じてLED、LCD、ブザーを制御する。

例：

- 800 ppm未満：緑
- 800〜1200 ppm：黄色
- 1200 ppm以上：赤またはブザー
- LCDにCO₂、温度、湿度を表示

この課題は、I2C、センサ、条件分岐、表示、出力を一度に復習できます。

# 漏れている、または強化した方がよい注意点

## 1. 電源と電圧

これは最優先で追記した方がよいです。

### サーボ

[サーボ制御のページ](https://github.com/foobarbazfred/Pico-MicroPython-Workshop/blob/main/3-Day1-Foundation/2-5-ServoControl.md)では、赤線を5Vに接続する説明がありますが、次の注意が必要です。

- サーボをPicoの3.3Vピンから給電しない
- サーボの電源電流、起動電流に注意する
- 外部5V電源を使う場合もPicoとGNDを共通にする
- サーボの動作でPicoがリセットすることがある
- サーボホーンが機械的に拘束されないようにする

### LCD

LCDを5Vで動かす場合、I2CのプルアップによってSDA/SCLが5Vになる構成には注意が必要です。Pico 2 WのGPIOは3.3V系なので、使用するLCDモジュールのI2C信号レベルを確認し、必要ならレベル変換を使う説明を入れるべきです。

### モータ

モータ制御では、以下を明記した方が安全です。

- モータをGPIOから直接駆動しない
- モータドライバを使用する
- 電源を分ける
- GNDを共通にする
- 逆起電力への対策
- 配線変更時は電源を切る

### ADC

[ADCのページ](https://github.com/foobarbazfred/Pico-MicroPython-Workshop/blob/main/3-Day1-Foundation/2-3-AnalogValue.md)では、0〜3.3Vの説明がありますが、以下を明記してください。

- ADC入力に3.3Vを超える電圧を加えない
- 可変抵抗の両端を3.3VとGNDに接続する
- 中央端子をADCピンに接続する
- 電圧計算値は理想値であり、実測誤差がある
- ADCピンを電源やGNDに短絡しない

## 2. Wi-Fi認証情報

[ネットワークのページ](https://github.com/foobarbazfred/Pico-MicroPython-Workshop/blob/main/3-Day1-Foundation/4-1-Network.md)にはSSIDとパスワードをソースコードに書く例があります。

教材では、次のような注意を強く表示した方がよいです。

> 実際のSSID、パスワード、APIキーをGitHubへコミットしないでください。

例としては、

- `secrets.py`
- `secrets.example.py`
- 環境変数
- 研修専用の一時的なWi-Fi

などを使う構成が適しています。

## 3. 公開MQTTブローカ

[MQTTのページ](https://github.com/foobarbazfred/Pico-MicroPython-Workshop/blob/main/3-Day1-Foundation/4-x-MQTT_Service.md)では、公開ブローカを利用しています。

教育目的では便利ですが、次の注意書きが必要です。

- 通信内容を他人に見られる可能性がある
- topic名が他の受講者と衝突する可能性がある
- 個人情報や秘密情報を送信しない
- `broker.emqx.io` のような公開サービスに大量送信しない
- TLS、認証、QoSの違いを説明する
- 研修終了後にtopicやクライアントIDを再利用しない

現在のtopicは受講者IDを使っていますが、`workshop/<session-id>/<team-id>/<device-id>/sensor` のように、研修回・チーム・機器を含める方が衝突しにくいです。

## 4. ネットワーク障害への対応

実際のワークショップでは、Wi-Fiや外部APIが動かないことが頻繁に起きます。

最低限、以下を教材化すると安心です。

- 接続タイムアウト
- DNS失敗
- HTTPステータスコード
- APIのレート制限
- MQTT切断時の再接続
- センサだけで動くオフラインモード
- Wi-Fiがなくても実施できる代替課題

# コード・資料上の具体的な修正候補

これは優先度が高いものです。

## 1. Wi-Fiコードに構文エラーがあります

[4-1-Network.md](https://github.com/foobarbazfred/Pico-MicroPython-Workshop/blob/main/3-Day1-Foundation/4-1-Network.md)の例に、

```python
else::
```

があります。これは次のように修正が必要です。

```python
else:
```

また、1秒待つだけでは接続完了を保証できないため、タイムアウト付きのループにした方が実用的です。

## 2. I2Cの`bytes()`例が不正です

[3-1-use-SerialBus.md](https://github.com/foobarbazfred/Pico-MicroPython-Workshop/blob/main/3-Day1-Foundation/3-1-use-SerialBus.md)の例に、

```python
data = bytes(0x00, 0x01, 0x02)
```

があります。

通常は次のように書きます。

```python
data = bytes((0x00, 0x01, 0x02))
```

同様に、

```python
data = bytes((0xFF, 0x00, 0x80, 0x3F))
```

とします。

## 3. SDカードのサンプルにimport漏れがあります

[SDカードのページ](https://github.com/foobarbazfred/Pico-MicroPython-Workshop/blob/main/3-Day1-Foundation/3-x-SPI-SDCard.md)では、

```python
from machine import Pin
from machine import SPI
```

としている一方、後で、

```python
cs = machine.Pin(...)
```

を使っています。

次のいずれかに統一する必要があります。

```python
import machine
from machine import Pin, SPI

cs = Pin(SD_CARD_CS, Pin.OUT, pull=Pin.PULL_UP)
```

または、

```python
import machine

cs = machine.Pin(SD_CARD_CS, machine.Pin.OUT, pull=machine.Pin.PULL_UP)
```

## 4. `json.loads(f)`は見直しが必要です

同じSDカードのページに、

```python
with open('/sd/config.json','r') as f:
   config = json.loads(f)
```

があります。

ファイルオブジェクトを直接渡すなら、通常は次のようにします。

```python
with open('/sd/config.json', 'r') as f:
    config = json.load(f)
```

文字列として読み込むなら、

```python
with open('/sd/config.json', 'r') as f:
    config = json.loads(f.read())
```

です。

## 5. CO₂センサのCRCチェック

SCD41のコードでは、9バイトのデータを読み込んでいますが、CRCを検証していません。

研修の最初の簡易例としてはよいですが、発展課題として、

- CRCの意味
- 通信エラーの検出
- CRC不一致時の扱い

を追加すると、センサドライバの理解が深まります。

## 6. Web APIのエラー処理

[WebAPIのページ](https://github.com/foobarbazfred/Pico-MicroPython-Workshop/blob/main/3-Day1-Foundation/4-2-WebAPI.md)には、エラー時に`data`を表示するコードがありますが、エラー時に`data`が定義されていない可能性があります。

```python
else:
    print("error:", response.status_code)
```

のようにするか、レスポンス本文を取得するようにした方が安全です。

また、HTTPレスポンスを使い終わった後に、

```python
response.close()
```

を呼ぶ例も入れた方がよいです。マイコンではメモリやソケットの解放が重要です。

## 7. Webサーバの安全性

`rp2_webserver.py`は教材としては面白いですが、現在のままでは次の注意が必要です。

- 認証がない
- ネットワーク上の誰でもGPIOを操作できる
- URLパラメータの検証が弱い
- HTTP通信が平文
- 実用用途にそのまま使わないことを明記する

「LAN内の実験専用」「インターネットに公開しない」と明確に書くべきです。

# 4-Day2-Practicalについて

ご指定どおり、ここは軽く確認しました。

方向性は良いですが、2日目の実践を成功させるためには、仕様書テンプレートを追加するとよいです。

```text
# プロジェクト名

## 目的
誰の、どんな問題を解決するか。

## 入力
センサ、スイッチ、Web APIなど。

## 出力
LED、LCD、音、サーボ、MQTTなど。

## システム構成
Pico、部品、サーバ、通信方式。

## 最小完成条件
最低限、何が動けば完成とするか。

## 発展条件
時間が余った場合に追加する機能。

## 役割分担
回路、MicroPython、ネットワーク、発表など。

## リスク
部品不足、通信障害、実装上の難所。
```

特に重要なのは「最小完成条件」です。

2日目にありがちな失敗は、最初から大きなアイデアを考え、最後まで動くものが完成しないことです。

例えば、

- 最低限：センサ値を取得してLEDに反映
- 標準：LCDやサーボを追加
- 発展：MQTTやWebダッシュボードを追加

のように、段階を決めておくと成功率が高くなります。

「梅・竹・松」という名称は面白い一方、難易度の意味が初見では分かりにくいため、次のように併記するとよいです。

```text
梅：GPIO・LED・スイッチ中心
竹：センサ・表示・複数デバイス
松：ネットワーク・Web API・MQTT
スーパ松：Node-RED・IoTプラットフォーム連携
```

# 推奨する改訂優先順位

## 最優先

1. Wi-Fiページの構文エラーを修正
2. I2C、SDカード、Web APIのサンプルコードを実行確認
3. 電源・電圧・GND共通の注意を追加
4. Wi-Fiパスワード、APIキー、公開MQTTの注意を追加
5. Pico W / Pico 2 W / RP2の表記を統一
6. 1日目の必須範囲を絞る

## 次に実施

1. 各章に「目標」「準備」「課題」「トラブルシューティング」を追加
2. GPIO番号・物理ピン番号の表を各ページに追加
3. 章番号とファイル名を整理
4. 1日目最後に統合課題を追加
5. 2日目に仕様書テンプレートと最小完成条件を追加

## 余裕があれば

1. チェックポイント形式の確認問題を追加
2. 完成コードと穴埋めコードを分ける
3. 受講者向け資料と講師向け資料を分離
4. 各サンプルに対応する動作確認済みバージョンを記載
5. GitHub上で課題提出用のテンプレートを用意

## 結論

この教材は、題材の豊富さと実機中心の構成が大きな強みです。特に、REPLを使った試行錯誤、センサと出力装置の組み合わせ、2日目のチームプロトタイプ開発は、一般的な入門教材より実践的です。

一方で、現状は内容が豊富すぎるため、受講者から見ると「何が必須で、どこまでできればよいか」が分かりにくくなっています。

まずは、

- 1日目の必須範囲を絞る
- 各章の到達目標を明記する
- コードを一度通しで実行確認する
- 電源・ネットワーク・セキュリティの注意を追加する
- 2日目の最小完成条件を定義する

という順番で改善するのがおすすめです。これだけでも、教材の分かりやすさとワークショップ当日の進行安定性はかなり向上すると思います。
