# 生成AIと組み込みアプリの連携

## 概要
本稿は「組み込みアプリ（マイコン）に対して生成AI（LLM等）をどのように連携できるか」を整理したものです。

組み込み機器は計算資源・メモリ・通信帯域に制約があるため、現実的なアプローチは「端末側の軽量処理（オンデバイス）と、生成AIを持つサーバ側の処理を適切に組み合わせる」ことです。本稿では実装アーキテクチャパターン、ユースケース、データフロー、注意点、導入パイロット案までを提示します。

---

## 先に結論
- 現実解はハイブリッド：端末での軽量判定（ウェイクワード／意図分類／閾値判定等）＋必要時にクラウドまたはエッジサーバの生成AIへ問い合わせ。
- 生成AIはユーザ機能（自然言語インタフェース等）だけでなく、開発支援（コード生成・テスト自動化）や運用支援（ログ要約・ドリフト検出）でも高い価値を発揮する。
- セキュリティ、プライバシー、レイテンシ、コストのバランスを設計で明確にし、必ず human-in-the-loop と監査ログを取り入れる。

---

## 実装アーキテクチャパターン
以下は組み込みアプリと生成AIを組み合わせる代表的パターンです。用途や制約に応じて選択・組合せます。

### パターンA：オンデバイス小モデル + クラウドLLM（標準的）
- デバイス: ウェイクワード検知、軽量意図分類、特徴量抽出（TF Lite Micro, Edge Impulse 等）
- 通信: MQTT/HTTPSで要約情報や特徴量を送信
- サーバ: LLM API（OpenAI等）で生成処理、必要に応じてベクトルDBを参照
- 利点: 低消費電力で即時応答、複雑処理はサーバへ
- 欠点: 通信依存・遅延・コスト・プライバシー問題

### パターンB：エッジサーバ配置（低遅延・プライバシー重視）
- デバイスは前処理のみ、生成と高負荷推論は近接エッジサーバで実行
- 公衆網を経由しないためプライバシー/レイテンシの面で有利

### パターンC：完全オンデバイス（限定的）
- MCU上では主にキーワード検出や小さなNN（意図判定）に限定
- SBC（Raspberry Pi等）ではローカルLLMを動かせるケースもあり得る

### パターンD：ハイブリッド・フェールセーフ
- 通常はオンデバイス判定、信頼度が低い場合や詳細説明が必要なときだけ生成AIへ問い合わせ
- オフライン時はローカル閾値判定でフォールバック

## 具体ユースケース（実装イメージ）

### 1) ユーザ向け：音声操作・対話
- ワークフロー: マイク → ウェイクワード（端末）→ 意図分類（端末）→ 詳細応答/説明は生成AIで生成
- 実装ポイント: 意図分類は小モデル（オンデバイス）、対話文生成はサーバにオフロード

### 2) ユーザ向け：状態説明とトラブルシュート
- デバイスはセンサ特徴量（統計・異常スコア）をまとめて送信
- 生成AIは自然言語での説明と暫定対処法を生成
- 重要: 生成された対処は「提案」として扱い、人の承認フローを明示

### 3) 開発支援：コード生成・テスト自動化
- データシート/仕様を与えてドライバやテストケースを生成
- 生成コードはCIで SAST・ユニットテストを必須化

### 4) 運用支援：ログ要約と原因推定
- 長いログは埋め込み→ベクトル検索で類似事例を探した上で、生成AIに要約・対応案を作らせる
- アラートの優先度付けや暫定対応を自動提案

### 5) モデル管理：デプロイとロールアウト
- モデルハッシュ、互換性チェックリスト、代表入力による回帰テストをCIで自動化し、合格後OTAで配布

---

## データフローとインタフェース設計
- 生データは原則送らない（高コスト／プライバシー懸念）。代わりに要約・統計・特徴量を送る。
- メッセージ形式（例）:
  - { device_id, timestamp, features: {...}, summary: "...", model_hash: "..." }
- 通信方式:
  - 即時対話: WebSocket / HTTP
  - バッチ解析: MQTT / HTTPS（バッチ送信）
- トレーサビリティ: プロンプト、モデルID、応答、タイムスタンプを保存

---

## 必要コンポーネント（候補）
- エッジ推論: TensorFlow Lite Micro, Edge Impulse
- マイコン実装: MicroPython, C/C++
- LLM / 生成AI: OpenAI, Anthropic, 自社ホスト型（Llama系）
- ベクトルDB: FAISS, Pinecone, Milvus
- 通信: MQTT, CoAP, HTTPS
- CI/CD: GitHub Actions, GitLab CI
- ログ収集/監視: ELK, Prometheus, Grafana

---

## セキュリティ・プライバシー・ガバナンス
- 機密データは匿名化・集計するか、オンデバイスで処理
- 外部LLM使用時はデータ取り扱い契約（DPA）と利用規約を必ず確認
- プロンプトとレスポンス、モデルIDは監査ログとして保管
- 生成コードはSAST/静的解析で自動チェックし、レビューを必須化
- フォールバック設計：通信切断時はローカル判定へ移行

---

## 実装上のトレードオフと注意点
- レイテンシ vs プライバシー vs コスト：要件に応じて優先順位を決める
- LLMの不確実性（hallucination）：事実確認できるデータソースと組み合わせる
- オフライン動作の設計：必ずオフライン時の最低限の振る舞いを定義
- モデルのバージョン管理と互換性を明確にする

---

## 具体的プロンプト例（開発・運用支援）
- 要件抽出: 「以下の会議録から機能要件と非機能要件を抽出してください。出力は箇条書きで。」
- テスト生成: 「以下の関数仕様に対して pytest テンプレートを作成してください。境界値テストを3つ含めること。」
- ログ要約: 「以下のシリアルログから頻出エラーと時系列要約を作成してください。」

---

## 小さなパイロット案（2週間）
- 目的: ログ要約→アラート優先付けによる運用工数削減を検証
- スコープ: 10台、過去30日ログ
- 実施手順:
  1. ログ整備（個人情報除去）
  2. 埋め込み化→ベクトルDB登録
  3. LLMで要約・原因候補生成
  4. 人間評価→フィードバック
  5. 効果測定（調査時間、誤検知率、運用コスト）

---

## 導入順序の提案
1. まずは開発支援（要件抽出・PR説明・テスト生成）から導入
2. 次に運用領域（ログ要約・アラート自動化）へ展開
3. ユーザ向け生成機能はフェーズを分けて慎重に実装（セキュリティとUX検証を並行）
